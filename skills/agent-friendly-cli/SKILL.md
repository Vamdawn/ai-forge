# Agent-friendly CLI

把 CLI 当作稳定的机器契约来设计或审查。先确认目标 CLI 的命令、输入、输出、错误和副作用，再用 [references/checklist.md](references/checklist.md) 逐项检查；不要因为某项未实现就臆造产品需求。

## 工作方式

1. **发现上下文**：读取项目说明、命令入口、现有 `--help`、schema、示例和测试。若是新 CLI，先列出命令、资源、读写操作和调用者需要完成的任务。
2. **选择模式**：
   - 设计/实现：为每个命令补齐可发现的参数、输入输出、退出码、错误和副作用契约；优先复用项目已有约定。
   - 审查：按清单逐项给出 `通过`、`部分通过` 或 `不通过`，每项附证据（文件、命令或帮助输出）。
3. **验证行为**：在无 TTY、管道、空输入、未知参数、失败、超时、重复写入和取消场景下运行可行的检查。涉及真实写操作时先使用 dry-run、测试环境或只读路径。
4. **报告结论**：按严重程度排序问题，并说明影响、最小修复建议和验证方式。无法从仓库证据判断的项目标记为“未知”，不要猜测。

## 必须守住的契约

- `stdout` 在机器输出模式下只包含声明格式的数据；日志、进度和诊断写 `stderr`。
- 参数错误、认证/权限、资源不存在、冲突、超时和部分完成应能通过稳定退出码与结构化错误区分。
- 错误至少能表达 `code`、`message`、`details`、`retryable` 和 `next_action`；列表响应支持游标，写操作支持幂等键或明确说明不可幂等。
- 破坏性操作必须有无 TTY 下可判断的确认策略；凭据不得进入 argv、输出或日志。
- 长任务、分页、字段投影、信号取消和环境自检都要有明确边界。

## 输出格式

审查报告使用下列顺序：

1. 范围与证据：检查了哪些命令、文件和运行场景。
2. 总体结论：通过项数、部分通过项数、不通过项数、未知项数。
3. 问题表：`严重程度 | 规则 | 证据 | 影响 | 最小修复 | 验证`。
4. 优先级行动：先修复阻断 Agent 正确调用或可能造成未预期副作用的问题。

设计任务则输出命令契约草案（参数、stdin、stdout、stderr、退出码、错误 schema、副作用和示例），并用同一清单复核。
